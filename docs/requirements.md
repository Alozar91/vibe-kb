# Функциональные требования (ТЗ)

- **Статус:** рабочий документ (v0.1, 2026-11-20)
- **Источники:** исходные требования заказчика (1–38), принятая концепция (`concept.md` v1.0), решения обсуждений (§16 концепции).
- **Соглашения:** каждое требование имеет ID (`АУТ-1` и т.п.), формулировку в терминах MUST (обязано) / SHOULD (желательно), **критерий приёмки** — проверяемое утверждение. Приоритет: если не указано иное — MUST. Изменения требований фиксируются здесь; номера исходных требований (1–38) сохранены для трассировки.
- **Связь с концепцией:** трассировочная матрица — в конце документа. Архитектура и обоснования — в `concept.md`, здесь только «что система должна делать».

## 1. Аутентификация и учётные записи (АУТ)

**АУТ-1. Вход по логину и паролю через домен** (исходное треб. 1, 2)
MUST: вход логином/паролем, пароль проверяется в корпоративном LDAP/AD (Keycloak User Federation); пользователь создаётся автоматически (JIT) при первом входе.
Приёмка: пользователь из AD входит паролем; в системе появляется пользователь с тем же `sub`/именем, что в AD; неверный пароль — отказ входа.

**АУТ-2. Сквозной вход с доменной машины (Kerberos/SPNEGO)** (исходное треб. 2)
MUST: при открытии сайта из браузера на доменной Windows-машине внутри доменной сети вход выполняется без ввода пароля (SPNEGO); principal сопоставляется с тем же LDAP-пользователем.
Приёмка: на настроенной доменной машине браузер (Edge/Chrome по GPO) входит в систему автоматически, без экрана логина; итоговый пользователь идентичен пользователю АУТ-1 (тот же account).

**АУТ-3. Локальные пользователи** (решение §16 п. 20)
MUST: возможна регистрация пользователя с логином/паролем без привязки к AD (локальный пользователь Keycloak) — для подрядчиков и внешних техучёток; блокировка таких пользователей — администратором Keycloak.
Приёмка: локальный пользователь входит паролем; админ Keycloak может его заблокировать; после блокировки вход невозможен.

**АУТ-4. Уход сотрудника** (решение §16 п. 20)
MUST: при блокировке учётной записи в AD вход в систему прекращается; роли в группах и авторство материалов при этом не удаляются (остаются в истории версий и аудите).
Приёмка: блокировка учётки в AD → вход невозможен; материалы автора по-прежнему отображаются, записи аудита сохранены.

**АУТ-5. Проверка токенов**
MUST: API и MCP принимают Bearer JWT от Keycloak; backend проверяет подпись (JWKS с кэшированием), `iss`, `aud`; операции выполняются от имени пользователя из `sub`.
Приёмка: запрос без токена / с чужим `aud` / с просроченным токеном — 401; запрос с валидным токеном — выполняется с правами владельца токена.

**АУТ-6. Отдельные Keycloak-клиенты** (решение §11.3 концепции)
MUST: клиенты `kb-web`, `kb-rag`, `kb-mcp`; политики «только service accounts» / «только интерактивные пользователи» задаются на уровне клиентов.
Приёмка: техучётка не может получить токен через интерактивный клиент `kb-web`; API кода не меняет.

## 2. Группы (ГРП)

**ГРП-1. Иерархия групп** (исходное треб. 4, 5)
MUST: группы образуют дерево произвольной глубины; группа может быть вложена в другую группу; циклы запрещены (проверка при создании и при перемещении).
Приёмка: создание подгруппы любой глубины; попытка зациклить дерево (переместить группу в её же потомка) — отказ.

**ГРП-2. Уникальность имён групп** (исходное треб. 13)
MUST: имя группы уникально среди не удалённых групп в рамках одной родительской группы, без учёта регистра и лишних пробелов (`lower(trim(name))`); удалённые группы не мешают созданию новых с тем же именем.
Приёмка: «Отчёты» и «отчёты  » в одном родителе — конфликт; то же имя в другой родительской группе — допустимо; после soft-delete группы имя освобождается.

**ГРП-3. Soft-delete групп и правило удаления** (исходное треб. 12; решение §16 п. 14)
MUST: удаление группы — только soft-delete; удалить группу нельзя, пока в её иерархии (включая вложенные) есть не удалённые материалы; подгруппы удаляются до родителя («снизу вверх»).
Приёмка: удаление группы с материалами — отказ с перечнем препятствий; после удаления групп/материалов внутри — удаление проходит; данные в БД сохранены.

**ГРП-4. Управление деревом** (решение §16 п. 18)
MUST: подгруппы создаёт Владелец родительской группы; переименование — Владелец группы; перемещение группы — при наличии права на создание подгрупп (Владелец) в обеих группах (старой и новой); удаление пустой группы — её Владелец; восстановление удалённой группы — только системным администратором.
Приёмка: Редактор не видит кнопок управления деревом; перемещение группы пользователем без роли Владелец в одной из двух групп — 403; восстановление доступно только админу.

**ГРП-5. Настройка чанкера на группе — только системный администратор** (исходное треб. 34)
MUST: назначение/изменение способа чанкования группы доступно только администратору системы (UI и API).
Приёмка: Владелец группы не имеет эндпоинта/кнопки настройки чанкера; запрос под его токеном — 403.

## 3. Материалы и версии (МАТ/ВЕРС)

**МАТ-1. Материал — минимальная единица, привязан к группе** (исходное треб. 3, 4)
MUST: каждый материал принадлежит ровно одной группе.
Приёмка: создание материала вне группы невозможно; перенос в другую группу — по МАТ-5.

**МАТ-2. Файл обязателен** (исходное треб. 6; решение §16 п. 22)
MUST: материал обязательно содержит файл; версия без файла невозможна; «безфайловые» материалы не создаются.
Приёмка: создание материала без файла — 422; у любого материала ≥1 версии с файлом.

**МАТ-3. Внешние ссылки** (исходное треб. 7; решение §16 п. 4)
MUST: материал может иметь несколько ссылок на внешние источники, каждая с меткой; ссылки входят в снимок версии — их правка создаёт новую версию.
Приёмка: добавление/правка ссылки создаёт новую версию; ссылка доступна в карточке и через API/MCP.

**МАТ-4. Уникальность имени материала** (исходное треб. 13)
MUST: имя материала уникально среди не удалённых материалов своей группы (`lower(trim(name))`, частичный индекс).
Приёмка: дубли имени в группе — 409; после soft-delete имя освобождается.

**МАТ-5. Перемещение материала** (решение §16 п. 18)
MUST: перенос материала в другую группу — при наличии права создания материалов (Редактор+) в обеих группах; проверяется уникальность имени в целевой группе; при изменении effective-чанкера запускается переиндексация.
Приёмка: перенос без прав в одной из групп — 403; дублирующее имя в целевой группе — 409; после переноса материал чанкуется по правилам новой ветки (если они отличаются).

**ВЕРС-1. Версионирование** (исходное треб. 25; решение §16 п. 22)
MUST: новая версия создаётся при изменении файла, описания, внешних ссылок или атрибутов; комментарий изменения обязателен; номер версии монотонный с 1.
Приёмка: правка любого из перечисленного — `version_no` + 1; правка только названия — новой версии нет (название не версионное); комментарий пуст — 422.

**ВЕРС-2. Дедупликация файлов и защита от ретраев** (решение §13.2)
MUST: если файл не менялся (тот же sha256), версия ссылается на прежний объект хранилища; правка без каких-либо изменений — отказ «ничего не изменилось»; повторная отправка запроса загрузки с тем же `Idempotency-Key` возвращает исходный ответ, второй версии нет.
Приёмка: двойная отправка формы (одинаковый ключ) — одна версия; две разные правки с одинаковым файлом — две версии, в хранилище один объект.

**ВЕРС-3. Индексируется только актуальная версия** (решение §16 п. 7)
MUST: в полнотекстовый и векторный поиск попадает только текущая версия; история версий доступна для просмотра и скачивания.
Приёмка: после создания новой версии старые чанки вытеснены из индекса; прошлые версии скачиваются, но не находятся поиском.

**ВЕРС-4. Родительские материалы** (исходное треб. 26–28; решение §16 п. 5)
MUST: у материала может быть не более одного родителя; детей может быть много; привязка фиксирует конкретную (актуальную на момент привязки) версию родителя; обновление родителя не меняет потомков; UI/API показывают расхождение «привязана версия N, актуальная M»; перепривязка/отвязка — операции редактирования (Редактор+), перепривязка фиксирует новую актуальную версию.
Приёмка: обновление родителя — у детей ничего не меняется, появляется индикатор; повторная привязка сбрасывает индикатор; вторая родительская связь — 409.

## 4. Статусы (СТАТ)

**СТАТ-1. Набор статусов** (исходное треб. 9)
MUST: статусы материала — Черновик, На проверке, Подтверждён, Архив, Удалён.
Приёмка: в системе ровно пять статусов; API и БД (enum) не принимают иных значений.

**СТАТ-2. Разрешённые переходы** (исходное треб. 10)
MUST: переходы — строго по списку: Черновик→На проверке; На проверке→Подтверждён; На проверке→Черновик; Подтверждён→Черновик; На проверке→Архив; Подтверждён→Архив; Черновик→Удалён. Все остальные — запрещены.
Приёмка: любой недопустимый переход (например, Черновик→Подтверждён, Архив→Черновик) — 409; переходы фиксируются в append-only журнале статусов.

**СТАТ-3. Семантика и конечные состояния** (исходное треб. 11; решение §16 п. 2, 3)
MUST: Архив и Удалён — конечные; восстановление из Удалён/Архив невозможно (только создание копии — новый черновик); редактирование Подтверждённого создаёт новую версию со сбросом статуса в Черновик.
Приёмка: попытка перехода из Архива — 409; правка подтверждённого — статус «Черновик», подтверждённым остаётся прежний снимок версии.

**СТАТ-4. Правила удаления** (исходное треб. 10, 12)
MUST: в «Удалён» — только из Черновика; удаление = soft-delete (`is_deleted=true`); удалённые материалы исключены из навигации и поиска для всех; право определяется ролью (Редактор и выше), автор — лишь атрибут.
Приёмка: удаление материала из «На проверке» — 409; удалённый материал не виден никому, включая автора; данные в БД сохранены.

**СТАТ-5. Автор и проверяющие** (исходное треб. 24; решение §16 п. 19)
MUST: у материала всегда есть автор; список проверяющих фиксируется в момент отправки на проверку (все пользователи с ролью Проверяющий в группе); подтвердить может любой из этого списка, его имя фиксируется (`confirmed_by/at`); у черновика поля проверяющих пусты.
Приёмка: после отправки на проверку в снимке версии — список Проверяющих группы; подтверждение другим пользователем (не из списка) — 403; отзыв роли Проверяющего после отправки не мешает подтвердить текущую проверку.

**СТАТ-6. Видимость по статусам** (решение §16 п. 9)
MUST: Читатель видит все статусы, кроме «Удалён»; «Удалён» не виден никому (события — в аудите).
Приёмка: читатель видит черновик группы, в которой он читатель; удалённый материал не отображается ни в каком интерфейсе.

## 5. Права доступа (ПРВ)

**ПРВ-1. Права на группу с наследованием вниз** (исходное треб. 15)
MUST: права выдаются на группу и действуют на все вложенные группы и материалы.
Приёмка: роль Читателя на корневой группе даёт чтение всего дерева.

**ПРВ-2. Навигационный доступ к предкам** (исходное треб. 16)
MUST: право на вложенную группу даёт видимость цепочки вышестоящих групп только для навигации — без содержимого (материалы предков и соседние ветки не видны).
Приёмка: пользователь с правом на «Оборудование→Насосы» видит «Оборудование» в дереве, но не список его материалов и не соседнюю ветку «Клапаны».

**ПРВ-3. Роли** (исходное треб. 30; решение §16 п. 1)
MUST: роли в группе — Читатель, Редактор, Проверяющий, Владелец; у одного пользователя в разных группах роли могут быть разными.
Приёмка: один и тот же пользователь — Владелец в группе A и Читатель в группе B.

**ПРВ-4. Матрица прав по ролям** (исходное треб. 31–33)
MUST: Читатель — только чтение; Редактор — чтение + создание/редактирование материалов, смена статусов (кроме подтверждения), soft-delete; Проверяющий — всё, что Редактор, плюс подтверждение и возврат на доработку; Владелец — всё, включая подтверждение, выдачу ролей и управление деревом подгрупп.
Приёмка: попытка подтверждения под Редактором — 403; попытка выдачи прав под Проверяющим — 403; все операции Владельца — успешны.

**ПРВ-5. Запрет по умолчанию и админ** (исходное треб. 35, 36)
MUST: нет явной роли — нет доступа (включая анонимов); системный администратор имеет полный доступ везде, минуя проверки.
Приёмка: пользователь без ролей видит пустое дерево; админ выполняет любую операцию в любой группе.

**ПРВ-6. Объединение прав** (решение §16 п. 8)
MUST: при наличии нескольких ролей в иерархии действует наиболее разрешающее объединение.
Приёмка: Редактор на родителе + Читатель на дочерней = Редактор внутри дочерней.

**ПРВ-7. Выдача ролей на вложенные группы** (решение по итогам ревью)
MUST: Владелец группы может выдавать роли на свою группу и любые вложенные в неё.
Приёмка: Владелец корня назначает Читателя на подгруппу 3-го уровня; Редактор не может выдавать роли никому.

**ПРВ-8. Bootstrap прав** (решение по итогам ревью)
MUST: первичные роли (владельцы корневых групп) выдаёт системный администратор.
Приёмка: до выдачи первичных ролей никто, кроме админа, не видит контент.

**ПРВ-9. Единая точка проверки** (исходное треб. 17, 18)
MUST: права проверяются на момент запроса во всех точках: UI/REST, поиск (фильтр результатов), RAG API, MCP; кэш прав инвалидируется при изменении ролей.
Приёмка: отзыв роли делает материал недоступным в UI, поиске, RAG и MCP немедленно, без переиндексации.

## 6. Чанкование и индексация (ЧНК)

**ЧНК-1. Автоматическая обработка файла** (исходное треб. 19)
MUST: при создании/обновлении файла автоматически запускается пайплайн: антивирус (гейт) → извлечение текста → чанкование → эмбеддинги → индекс; операция асинхронная (очередь).
Приёмка: после загрузки через N минут материал находится поиском; сбой на шаге виден в статусе задачи и не делает материал недоступным для скачивания.

**ЧНК-2. Стандартные чанкеры** (исходное треб. 20)
MUST: встроены: по символам (фикс. размер + overlap), рекурсивный, parent-child (мелкие для поиска, родительские — в контекст LLM), по предложениям/абзацам, токен-базированный, разметко-ориентированный (Markdown/HTML), таблично-ориентированный (лист/CSV → группы строк с повторением заголовков; в метаданных — лист и диапазон строк).
Приёмка: каждый стандартный чанкер выбирается в настройке группы и даёт воспроизводимые (детерминированные) чанки.

**ЧНК-3. Кастомные чанкеры без пересборки** (исходное треб. 21)
MUST: кастомный чанкер — Python-файл в каталоге плагинов; загрузка администратором; регистрация через админ-эндпоинт «перечитать плагины» без пересборки и перезапуска API; контракт: `BaseChunker` с `name`, `version`, `chunk(source, params) -> list[Chunk]`.
Приёмка: добавление нового `.py`-файла + вызов эндпоинта → чанкер доступен в настройках групп; код плагина не менялся при этом в ядре системы.

**ЧНК-4. Разрешение способа по иерархии** (исходное треб. 22)
MUST: для материала действует настройка **самой вложенной** группы в его цепочке, у которой она задана (даже если это не группа материала напрямую).
Приёмка: дерево Корень(recursive)→B→C→D(parent_child): материал в D — `parent_child`; в C — `recursive`; в E — системный дефолт.

**ЧНК-5. Системный дефолт** (исходное треб. 23)
MUST: если ни одна группа в цепочке не настроена — применяется системный способ по умолчанию.
Приёмка: материал в группе без настроек в цепочке индексируется дефолтным чанкером.

**ЧНК-6. Контракт `ChunkSource`** (решение по итогам обсуждения)
MUST: чанкер получает `source`: `bytes` (всегда), `local_path` (read-only копия), метаданные файла (`mime`/`filename`/`size`/`sha256`, детектированные по содержимому), `meta` (материал/группа/версия/атрибуты), `text` (ленивый плоский текст стандартного экстрактора, кэшируется; `None`, если экстракция не удалась/не применима). Контракт — чистая функция без разделяемого состояния.
Приёмка: чанкер, работающий только с байтами, не триггерит извлечение текста; `text=None` не является ошибкой контракта; ошибка чанкера → задача индексации падает с понятной ошибкой, документ остаётся доступным для скачивания.

**ЧНК-7. Детекция типа и реестр экстракторов** (решение по итогам ревью)
MUST: тип файла определяется по содержимому (магические байты) при загрузке; заявленные клиентом тип/расширение — только для отображения; по детектированному типу выбирается экстрактор (pdf/docx/xlsx/csv/txt/md/html); исход фиксируется (`text_extracted`: успех/ошибка/не поддерживается) с метрикой и списком «документов без текста» в админке.
Приёмка: файл с расширением `.txt`, являющийся PDF, индексируется как PDF; изображения — `text_extracted=не поддерживается`, поиск по ним только по метаданным.

**ЧНК-8. Повреждённая настройка чанкера** (решение по итогам ревью)
MUST: если чанкер, на который ссылается настройка группы, отсутствует или не загружается — применяется системный дефолт, а в админке фиксируется предупреждение по затронутым группам.
Приёмка: удаление файла плагина не останавливает индексацию новых документов; предупреждение видно админу.

**ЧНК-9. Переиндексация** (решение §9.3)
MUST: изменение настройки чанкера группы или системного дефолта запускает фоновую переиндексацию затронутых материалов (только тех, у кого изменился resolved-чанкер); смена эмбеддинг-модели — полная переиндексация; операции идемпотентны.
Приёмка: после смены конфигурации в поддереве материалы этого поддерева переиндексированы, остальные — нет; повторный запуск не дублирует чанки.

## 7. Поиск (ПСК)

**ПСК-1. Четыре режима** (исходное треб. 14)
MUST: поиск — полнотекстовый (FTS Postgres, `ts_rank_cd`), по значениям атрибутов и метаданным (jsonb+GIN), векторный (KNN по эмбеддингам чанков), гибридный (RRF-объединение FTS и векторного).
Приёмка: каждый режим возвращает релевантные результаты по фиксированному тестовому корпусу; гибрид объединяет выдачи FTS и векторного.

**ПСК-2. Поиск по группам** (исходное треб. 14)
MUST: выдача поиска включает группы (по названию/описанию) с учётом навигационной видимости.
Приёмка: поиск «насосы» находит и группу «Насосы», и материалы внутри неё (в пределах прав).

**ПСК-3. Фильтр-фасеты** (решение §16 п. 16)
MUST: над результатами — агрегированные счётчики по атрибутам, статусу, группе, кликабельные, пересчитываемые под текущий запрос.
Приёмка: счётчики фасетов соответствуют числу результатов при применении соответствующего фильтра.

**ПСК-4. Права и неполные материалы** (решение §8.3, §9.2.1)
MUST: все режимы фильтруют выдачу по правам на момент запроса; материалы без извлечённого текста участвуют только в поиске по метаданным; прошлые версии не ищутся.
Приёмка: два пользователя с разными правами получают разные результаты по одному запросу; отзыв роли мгновенно меняет выдачу.

**ПСК-5. Языки** (решение §16 «Локализация»)
MUST: стартовые конфигурации FTS — русский и английский; смешанные документы индексируются в обеих конфигурациях с OR; перечень конфигураций расширяем; эмбеддинг-модель — мультиязычная.
Приёмка: документ со смешанным текстом находится и русским, и английским запросом.

## 8. RAG и MCP (РАГ)

**РАГ-1. RAG API** (исходное треб. 17)
MUST: `POST /api/v1/rag/query` — retrieval (чанки с цитатами: материал, версия, чанк, score, deep-link) и генерация ответа LLM (`with_answer`) с `[n]`-цитатами; `group_ids` фильтруются по правам запрашивающего; вложенные группы включаются автоматически; стриминг — SSE.
Приёмка: ответ на вопрос по документам группы содержит цитаты, ведущие к конкретным версиям; группы без прав исключены; запрос от имени пользователя без прав на группу — пустой результат.

**РАГ-2. MCP-сервер** (исходное треб. 17, 18)
MUST: MCP (Streamable HTTP, официальный Python SDK) с инструментами: `search`, `list_tree`, `get_material`, `read_chunks`/`read_file`, `rag_answer` — все под правами пользователя, от имени которого выполнен запрос (токен пользователя или техучётки).
Приёмка: MCP-клиент под токеном Читателя не может изменить данные; `rag_answer` возвращает тот же ответ, что RAG API с теми же правами.

**РАГ-3. Модели по OpenAI-compatible API** (исходное треб. 37)
MUST: все вызовы эмбеддингов и LLM — через настраиваемый OpenAI-совместимый эндпоинт (`base_url`, `api_key`, модели); смена модели эмбеддингов запускает полную переиндексацию.
Приёмка: переключение на другой эндпоинт/модель не требует правок кода; после смены модели эмбеддингов индекс перезалит.

## 9. Просмотр и скачивание (ПРС)

**ПРС-1. Скачивание через API** (исходное треб. 8; решение §16 п. 23)
MUST: оригинал доступен для скачивания всегда и только через API (авторизация и аудит в одном месте); presigned URL — отложенная оптимизация, при появлении выдача ссылки фиксируется в аудите.
Приёмка: скачивание фиксируется в аудите (кто/когда/что); доступ без права чтения — 403.

**ПРС-2. Просмотр в браузере** (исходное треб. 8; решение по итогам ревью)
MUST: унификация через PDF: офисные форматы и HTML/SVG конвертируются в PDF (LibreOffice headless, асинхронно, кэш на версию); PDF и растровые изображения отдаются как есть; TXT/MD/CSV рендерит фронт с экранированием; прямого рендера HTML/SVG нет (защита от XSS); до готовности — «превью готовится»; доступ к файлу — только после прохождения антивирус-скана.
Приёмка: DOCX отображается как PDF; HTML не исполняется в браузере; файл, не прошедший скан, недоступен для просмотра и скачивания.

## 10. Уведомления (УВЕД)

**УВЕД-1. Каналы** (решение §16 п. 12)
MUST: канал MVP — email; доставка через очередь с абстракцией «канал» (расширение — без переделки); SMTP-учётные данные — секрет в env.
Приёмка: письмо уходит по факту события; подмена SMTP-конфигурации не требует правок кода; креденшелы отсутствуют в БД.

**УВЕД-2. Подписка событий по ролям** (решение §16 п. 12)
MUST: системная настройка определяет, какие события каким типам ролей доставляются; пример: Проверяющий получает уведомление о новом материале в любой группе, где он Проверяющий.
Приёмка: отключение подписки в настройках прекращает доставку соответствующих событий; получатель «родительский материал обновился» — авторы дочерних материалов.

**УВЕД-3. Базовые события** — материал создан; отправлен на проверку; подтверждён; возвращён на доработку; отправлен в архив; выданы/изменены права; родительский материал обновился.
Приёмка: каждое перечисленное событие присутствует в справочнике `notification_events` и доступно для выбора в настройке подписок (УВЕД-2). MUST.

## 11. Нефункциональные требования (НФТ)

**НФТ-1. Аудит** (решение §16, §15)
MUST: фиксируются все изменяющие операции (материалы, версии, статусы, права, настройки), доступ к файлам (просмотр/скачивание), административные действия; записи неизменяемы.
Приёмка: любое действие пользователя находится в журнале с субъектом, временем и объектом; записи не редактируются и не удаляются через API.

**НФТ-2. Резервное копирование**
MUST: регулярные бэкапы Postgres (pgBackRest) и данных Silo; периодическая сверка целостности (объекты S3 ↔ записи БД). Кластеризация/HA — вне рамок текущей стадии.
Приёмка: восстановление из бэкапа на тестовом стенде проходит успешно; сверка фиксирует расхождения (если есть).

**НФТ-3. TLS**
MUST: TLS на боевом/приёмочном стенде; dev/локальные стенды — без TLS.
Приёмка: приёмочный стенд доступен только по HTTPS.

**НФТ-4. Антивирус** (решение §16 п. 10)
MUST: скан — обязательный шаг пайплайна и гейт доступа к файлу; на время разработки — заглушка (фоновая задача имитирует проверку); до завершения файл недоступен для скачивания и просмотра; превью генерируется только после скана.
Приёмка: сразу после загрузки (до «прохождения» скана) файл 403/404 для скачивания; после завершения — доступен.

**НФТ-5. Лимиты и секреты**
MUST: лимит размера файла — 50 МБ (настраиваемый), лимиты задаются в настройках системы в БД (админка), не через env; секреты (SMTP, ключи моделей, креденшелы хранилищ) — только через env.
Приёмка: файл больше лимита — 413; креденшелы не хранятся в БД и не попадают в ответ API.

**НФТ-6. Мониторинг**
MUST: метрики Prometheus: глубина очередей, лаг индексации, ошибки конвертации/индексации, время поиска; алерты.
Приёмка: дашборд показывает перечисленные метрики; при остановке воркеров растёт лаг индексации и срабатывает алерт.

**НФТ-7. Локализация**
MUST: интерфейс — русский; языки документов — любые (см. ПСК-5).
Приёмка: все тексты UI на русском; англоязычный документ полноценно ищется.

**НФТ-8. Ориентиры нагрузки** (решение §16 п. 13)
MUST: система рассчитана на 100–200 пользователей (всего), до 100 тыс. документов; RPS поиска — невысокий.
Приёмка: нагрузочный sanity на корпусе, эквивалентном 100 тыс. документов, показывает время поиска в пределах SLA (значение фиксируется при проектировании Этапа 1).

**НФТ-9. Идемпотентность** (решение §13.2)
MUST: все операции идемпотентны. Ключи: загрузка файла — `Idempotency-Key` клиента (обязателен) + дедупликация `FILE_OBJECT` по sha256; задачи пайплайна — `version_id` + шаг (`av`/`extract`/`chunk`/`embed`/`preview`), артефакты переписываются; чанки — атомарная замена по `version_id`; вектора — upsert по `chunk_id`; переходы статусов — append-only журнал с уникальностью по `request_id` + отсечение машиной состояний (ключ «версия+статус+автор» недопустим); уведомления — `event_id`+получатель; уникальные индексы БД — последний рубеж.
Приёмка: повтор запроса/задачи в любой комбинации не создаёт дублей (количество версий/чанков/переходов/писем инвариантно); обрыв воркера на полпути → продолжение с последнего завершённого шага без искажения данных.

**НФТ-10. Soft-delete**
MUST: материалы и группы не удаляются физически; физическая очистка — только отдельной процедурой администратора, вне обычного потока.
Приёмка: после soft-delete строки присутствуют в БД со флагом; прямые запросы к БД видят данные.
