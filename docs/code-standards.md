# Правила построения кода (Code Standards)

- **Статус:** принят (v1.0, 2026-11-20)
- **Основа:** концепция §3 (архитектура), §8.3 (единая точка прав), §13.2 (идемпотентность); решения: **прагматичный UoW**, **sync-first**.
- Назначение: единообразная структура кода для всех, кто подключается к проекту. Нарушения — через ревью.

---

## 1. Общие принципы

1. **Модуль = вертикальный срез по доменной области** (groups, materials, versions, statuses, search, indexing, rag, mcp, notifications, admin), а не «техническая» папка. Внутри среза — одинаковая структура (§2.1, §3.1).
2. **Направление зависимостей строгое:** `api → services → repositories → models`. Воркеры и MCP импортируют **только сервисы**; роутеры никогда не импортируются из других слоёв.
3. Общий код — только в `common/` (ошибки, security, authz, конфиг, идемпотентность). Срезы не импортируют внутренности друг друга.
4. Хендлеры тонкие: parse (pydantic) → authz → service → serialize. Бизнес-логики в хендлерах нет.

## 2. Backend — Python 3.12+ / FastAPI / SQLAlchemy 2

### 2.1 Структура каталогов

```
backend/
  app/
    main.py                 # сборка приложения: только wiring, без логики
    common/
      config.py             # pydantic-settings; все env-переменные в одном месте
      errors.py             # доменные исключения + маппинг в problem+json (api-spec §1)
      security/             # проверка JWT, извлечение пользователя (АУТ-5)
      authz.py              # ЕДИНСТВЕННАЯ точка проверки прав (ПРВ-9)
      idempotency.py        # middleware Idempotency-Key + кэш (НФТ-9)
      keys.py               # детерминированные ключи задач пайплайна
      db.py                 # engine, session-factory, UoW-контекст
    domain/                 # вертикальные срезы
      groups/               # api.py · schemas.py · service.py · repository.py
      materials/
      statuses/
        transitions.py      # таблица переходов §6 как данные
      search/
      indexing/             # пайплайн: извлечение → чанкование → эмбеддинги
      notifications/
      admin/
    models/                 # ORM-модели (по data-model.md); срезы их не переопределяют
    workers/                # задачи Celery: тонкие обёртки над сервисами
    mcp/                    # MCP-сервер: тоже только сервисы
  migrations/               # Alembic
  plugins/chunkers/         # кастомные чанкеры (ЧНК-3), монтируется как volume
  tests/
```

### 2.2 Слои и транзакции (прагматичный UoW)

- **api.py** — парсинг, authz, вызов сервиса, сериализация. Без SQL и ORM-объектов в ответах.
- **service.py** — бизнес-логика; принимает сессию и pydantic-схемы; возвращает DTO. Не знает про HTTP.
- **repository.py** — только там, где запросы нетривиальны (права/видимость, поиск, чанки); имена методов — доменные термины. Абстрактных репозиториев на каждую сущность не заводим.
- **Транзакции:** граница = один use-case. Для HTTP — сессия на запрос, `commit` после успешного сервиса, rollback при исключении. Сервисы **не делают commit сами**. Пример атомарных границ из НФТ-9: переход статуса + запись в журнал + обновление материала; замена чанков версии.
- **Машина состояний — как данные:** таблица переходов §6 — константа в `statuses/transitions.py`; сервис валидирует по ней; API отдаёт доступные переходы, фронт их рисует (правила не дублируются на фронте).
- **Исключения:** доменные (`StatusTransitionError`, `PermissionDenied`, `NameConflict`, `NothingChanged`, `FileNotScanned`) → маппинг в problem+json в `common/errors.py`.

### 2.3 Sync-first

- Сервисы, репозитории, модели — синхронные; хендлеры FastAPI — обычные `def` (FastAPI выполняет их в threadpool).
- **async — только на краях:** SSE-стриминг RAG (`domain/search` — async-обёртка над синхронным сервисом) и MCP-сервер. Async-код не смешивается с синхронными сервисами.
- Воркеры Celery — синхронные, используют те же сервисы с собственной сессией.

### 2.4 Качество и конвенции

- Типизация на публичных границах обязательна; `ruff` (вкл. isort) + `mypy` в CI; мерж только зелёный.
- Тесты: сервисы — юнит-тесты на тестовой сессии; репозитории/поиск — testcontainers (PostgreSQL+pgvector, Valkey, Silo); контрактные тесты по OpenAPI-схеме.
- Конфиг — только через `common/config.py` (pydantic-settings, префикс `KB_`); `os.getenv` в коде запрещён; секреты только env (НФТ-5).
- Миграции Alembic: аддитивные, без бизнес-логики (data-model §16).
- Имена сервисных функций — глаголы домена (`create_material`, `submit_for_review`), без `do_`/`handle_`.

## 3. Frontend — React + TypeScript + Ant Design 5

### 3.1 Структура (feature-sliced)

```
frontend/src/
  app/            # провайдеры, роутер, ConfigProvider (тема Ant)
  pages/          # маршруты; композиция виджетов, без бизнес-логики
  features/       # доменные фичи: materials/, statuses/, authz/, upload/
    …/api/        # вызовы API фичи
    …/model/      # логика (доступные переходы, права, валидация форм)
    …/ui/         # компоненты фичи
  entities/       # типизированные API-клиенты и типы — генерация из OpenAPI
  shared/         # api-client (http + OIDC-токен), обёртки Ant, lib/
```

### 3.2 Правила

- Вызовы API — **только** в `entities/*/api` и `shared/api-client` (инъекция OIDC-токена, обработка 401/409/423 из api-spec).
- Серверное состояние — **TanStack Query**; локальное UI-состояние — `useState`/Context; глобального стора для серверных данных нет.
- Бизнес-логика вне компонентов: «можно ли подтвердить/вернуть/в архив» считает функция в `features/statuses/model` по данным от API; в JSX — только рендер.
- Права в UI — через `can()` из `features/authz` (источник — `/users/me`); гейды декларативные.
- Типы API генерируются из OpenAPI (`openapi-typescript`); ручные типы запросов/ответов запрещены.
- Ant Design импортируется напрямую; тема — только через `ConfigProvider` (design tokens), без ad-hoc CSS.
- Роутинг — react-router; страницы — lazy.
- Качество: ESLint + Vitest + `tsc --noEmit` в CI.

## 4. Git и CI

- Ветки: `feat/<область>-<кратко>`, `fix/…`; документация — ветка `docs` (существующая практика).
- Коммиты: conventional (`feat:`, `fix:`, `docs:`, `chore:`); **каждый коммит сразу в origin** (правило владельца).
- Merge — `--no-ff` в `master`; мерж только при зелёном CI.

## 5. Что сознательно НЕ фиксируем

- Форматирование и мелкие стили — дефолты `ruff`/`prettier` (конфиги в репозитории), чтобы не спорить в ревью.
- Абстрактные репозитории и DI-контейнер — отклонены осознанно (см. §2.2; обоснование — `docs/adr/adr-0004-pragmatic-uow.md`); пересмотр — только через ADR.
