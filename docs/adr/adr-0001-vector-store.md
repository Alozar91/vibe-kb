# ADR-0001: Векторное хранилище — pgvector (старт), Qdrant по триггерам

**Статус:** принято · **Дата:** 2026-11-20

## Контекст

Требуется векторный и гибридный поиск по чанкам (ПСК-1, треб. 14). Ожидаемые объёмы: 100–200 пользователей, до 100 тыс. документов (сотни тысяч — единицы миллионов чанков). Команда небольшая, эксплуатационные расходы важны.

## Решение

Хранить чанки и вектора в PostgreSQL через **pgvector** (HNSW, `halfvec`, итеративные сканы 0.8.x). Полнотекстовый поиск — встроенный FTS Postgres, гибрид — RRF в приложении. Векторный слой — за абстракцией `VectorStore` (upsert/delete/search/filter).

## Альтернативы

- **Qdrant** — принят как целевой при росте: нативный BM25-sparse + RRF/DBSF, шардинг/репликация. Отклонён на старте из-за второго stateful-сервиса, двойной записи и несогласованности «Postgres + Qdrant».
- **OpenSearch/Algolia** — избыточны для MVP.

## Последствия

- (+) Один бэкап, атомарность «файл→чанки→вектора→права», SQL JOIN-фильтры по правам и атрибутам (ПРВ-9) без синхронизации ACL.
- (+) Меньше движущихся частей на MVP.
- (−) Вертикальный потолок масштаба; нет нативного BM25 (опция — ParadeDB `pg_search`).
- Триггеры миграции на Qdrant зафиксированы в concept §14: >10–20 млн активных чанков, p95 вне SLA, потребность в шардинге.
