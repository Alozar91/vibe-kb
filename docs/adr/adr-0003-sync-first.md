# ADR-0003: Sync-first бекенд

**Статус:** принято · **Дата:** 2026-11-20

## Контекст

FastAPI поддерживает async и sync-хендлеры; SQLAlchemy 2 умеет оба режима. Нагрузка невысока (100–200 пользователей, невысокий RPS), тяжёлые операции уйдут в Celery-воркеры. В команде не предполагается опыта промышленного async-Python.

## Решение

Сервисы, репозитории и модели — **синхронные**; HTTP-хендлеры — обычные `def` (FastAPI выполняет их в threadpool). Async применяется только там, где он нужен по существу: SSE-стриминг RAG-ответов и MCP-сервер. Async-код не вызывает синхронные сервисы напрямую.

## Альтернативы

- **Async везде** (asyncpg + async-сервисы) — единообразие «сверху вниз», но: async-заразность всех слоёв, сложнее транзакционные границы UoW, сложнее тесты, тонкие места с Celery (синхронным по природе). Выигрыш по пропускной способности при наших нагрузках отсутствует.

## Последствия

- (+) Простой, отлаженный стек; простые тесты; лёгкая интеграция с Celery.
- (+) Threadpool FastAPI снимает блокировки ввода-вывода без ручной асинхронщины.
- (−) Пул потоков — общий ресурс: тяжёлые синхронные вызовы (LLM/эмбеддинги HTTP) должны иметь таймауты и не блокировать пул надолго; при росте нагрузки — пересмотр (новый ADR).
