# ADR-0004: Прагматичный Unit of Work

**Статус:** принято · **Дата:** 2026-11-20

## Контекст

Атомарные границы зафиксированы в НФТ-9 (переход статуса + журнал + материал; замена чанков версии; загрузка файла + регистрация объекта). Один и тот же сервис вызывается из API, воркеров и MCP (§8.3). SQLAlchemy 2.0, ~15 таблиц.

## Решение

**Сессия SQLAlchemy = UoW на use-case**: HTTP-запрос — сессия на запрос (commit после успешного сервиса, rollback при исключении); фоновый шаг — сессия на шаг. Сервисы не делают commit сами. Слой репозиториев — только там, где запросы нетривиальны (права/видимость, поиск, чанки); в остальном — прямые запросы SQLAlchemy в сервисах. Абстрактные репозитории на каждую сущность и DI-контейнер не вводим.

## Альтернативы

- **Полный Clean Architecture** (репозиторий-интерфейсы на каждую сущность, DI) — строже для тестов, но церемониал непропорционален масштабу; пересмотр — новым ADR при росте команды/сложности.
- **Без явного UoW** (commit внутри сервисов) — риск незакрытых атомарных границ из НФТ-9 при вызовах сервисов друг из друга.

## Последствия

- (+) Атомарность гарантирована на ровно тех местах, где требует НФТ-9; сервисы вызываемы из трёх точек входа.
- (+) Тестируемость: сервис принимает сессию (testcontainers в интеграционных тестах).
- (−) Дисциплина: ревью следит, чтобы commit не появился внутри сервисов; сложные use case с несколькими транзакциями — явно разбиваются на шаги (пайплайн, НФТ-9).
